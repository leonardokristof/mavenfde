**Strongest case against the Week 1 verdict.** All four boxes are ticked, and
the questions keep changing shape: a follow-up about the PM, fifteen addresses
on one street, an AAMS number typed as a ticket or a card. With a fixed pipeline
every new kind of question means changing code by hand, while an agent with the
same read-only tools could combine them on its own and cover cases nobody has
written a path for yet.

**Week 3, the non-text content.** Fiberly has none today: everything it reads is database fields and
technicians' notes. The first to arrive would be screenshots that operators paste from AAMS or FIS screens.

1. **Visual, or text as pixels?** Text as pixels. A system screen holds IDs, a status and a task, not a picture anyone has to interpret.
2. **Does the number live only in the pixels?** Yes, the ID or the status on a pasted screen. Nothing has to find the image, because it comes in with the question. OCR inside the network reads it, and code checks the reading: the format, that the ID exists in the address register or in AAMS, and that the record it finds has the address or task shown on the same screen.
3. **Descriptions, or one parse per image?** Neither is needed for search: one OCR pass per screenshot when it is pasted, on the company's approved endpoint, never a batch over a corpus. If field photos ever join the records, the technicians' notes are the descriptions to index first.
4. **Video or audio?** None. A voice message from the field would come in typed out, and the transcript is enough, because the answer needs only the ID or address said in it.
